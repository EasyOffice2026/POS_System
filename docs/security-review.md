# Security review

**Date:** 16 October 2026 (Phase 6, step 2). **Scope:** the API, the web app, the print bridge, the CI pipeline and the database setup, as on `main` after Phase 5.

This review checks what the code does today, adds the checks that were missing, and lists what must be decided or done before launch. The tests named here run in CI on every pull request.

## Summary

No serious problem was found. Every API route refuses a request without a valid sign-in, and every route but two refuses a person without the right permission; a test now proves this for every route, including routes added later. Three things were added: security headers on every API answer, a refusal to start production with the development secret, and a package check in CI. Five points remain for the launch (see the last section).

## What was changed

1. **A test of every route** (`apps/api/src/security/routes.test.ts`). It reads the routes from the app itself, so a new route cannot be forgotten. Without a token, every route but the four public ones (health, sign-in, refresh, sign-out) must answer 401. With a valid token that has no permissions, every route but the two listed above must answer 403. A forged token, a changed token and a token without an algorithm must answer 401. Removing the permission check of one route makes this test fail, which was tried.
2. **Security headers on every API answer** (`apps/api/src/middleware/security-headers.ts`): nothing in an answer can run or be shown in a frame (`Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`), browsers do not guess its type (`X-Content-Type-Options: nosniff`), no address leaks to other sites (`Referrer-Policy: no-referrer`), answers are not kept by browsers or proxies (`Cache-Control: no-store`), and in production the browser uses HTTPS only for a year (`Strict-Transport-Security`).
3. **Production refuses the development secret** (`apps/api/src/config.ts`), and `.env.example` shows how to make a real one.
4. **CI checks the packages** (`npm audit --omit=dev --audit-level=high`): a known high or critical problem in a package the apps ship with stops the pull request.

## Before launch

These need a decision or belong to the production setup (Phase 6, step 4).

1. **HTTPS everywhere.** The web app and the API must be served over HTTPS only; the sign-in cookie is marked secure in production and is not sent over plain HTTP.
2. **Headers for the web app.** The host that serves the web app should send its own headers: a content security policy that allows only its own scripts and the API (`default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'`), `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`.
3. **Secrets on the server.** `JWT_ACCESS_SECRET` and the database password live in the host's secret settings, never in a file in the repository; changing the secret signs everybody out, which is how to react to a leak.
4. **Supabase.** The tables are in the `pos` schema, which Supabase does not publish through its Data API by default. Check in the Supabase dashboard (Settings, Data API, exposed schemas) that `pos` is not listed, and keep the service role key unused and private.
5. **Changes of rights take up to 15 minutes.** A person who is switched off or loses a permission keeps their current access token until it ends (at most 15 minutes); their sessions end at once. If the client wants it immediate, the API can check the person on every request, at a small cost.

Open questions that touch privacy are in the specs: whether customers agree to their phone number being kept (spec 022), and how long the audit log is kept.
