Executive Summary

This document presents the complete system design and technical proposal for a modern, web-based Multi-Brand Food & Beverage Point of Sale (POS) system. The platform is designed to support multiple brands operating across multiple branches, with full bilingual support in Arabic and English.

The system goes beyond a traditional POS to deliver an integrated operations platform covering the full restaurant lifecycle — from order placement and kitchen management, to inventory tracking, recipe costing, purchase management, customer loyalty, and business analytics. It is built to scale from a single outlet to a large F&B group with dozens of brands and branches.

Multi-Tenancy Model

Shared database with row-level tenant isolation. Each Brand is the top-level tenant; Branches belong to a Brand. All operational tables carry brand_id and branch_id, enforced at the API middleware level.

Tenant Level
Brand (e.g., "Pizza Palace", "Burger Hub")
Operational Level
Branch (e.g., "Pizza Palace — Mall Branch")
Data Isolation
Row-level via brand_id + branch_id on all tables
Cross-Brand Access
Group Admin role only, scoped by JWT claims
Branch Config
Independent menu pricing, operating hours, and printer settings per branch

Bilingual Architecture (AR / EN)

All UI strings use i18next. Database content stores translations inline as JSONB: name: { "en": "Grilled Chicken", "ar": "دجاج مشوي" }. The frontend applies dir="rtl" or dir="ltr" based on user preference. Tailwind RTL plugin handles automatic layout mirroring.

Loyalty Program

The loyalty program rewards repeat customers across every brand in the group. Customers join at the POS with their mobile number — no app or card is needed. Points are held in a group-wide wallet by default, so a guest can earn at one brand and redeem at another; each brand can instead be set to run its own separate program. All values below are defaults and can be changed from the Management Console without code changes.

Member ID
Mobile number (unique); optional name, email, birthday, and marketing consent
Scope
Group-wide points wallet (default) or brand-only, configurable per brand
Earn Rate
1 point per SAR 1 paid, after discounts, multiplied by the member's tier. Not earned on the part paid with points
Redemption Value
100 points = SAR 5, used as a payment tender at checkout
Redemption Limits
Minimum 500 points; up to 50% of the bill; one-time SMS code (OTP) required
Point Expiry
12 months after the points were earned (oldest points used first)
Bonuses
Sign-up bonus (50 pts), birthday reward, and double-points campaigns via the Promotions engine
Delivery Platforms
Talabat / Deliveroo / Jahez orders do not earn by default (the platform owns the customer); direct delivery orders do

Loyalty Flow at the POS

1
Identify Member

Cashier enters the customer's mobile number. The member's name, tier, and points balance appear on the order. New customers are enrolled in one step.

2
Build the Order

Items, modifiers, and discounts are added as normal. The cart shows the points the customer will earn.

3
Redeem (Optional)

At payment, points are applied as a tender. An OTP is sent to the member's mobile and entered by the cashier to confirm.

4
Earn & Receipt

When the order is settled, points are posted to the member's account. The receipt shows points earned, points redeemed, and the new balance.

5
Voids & Refunds

Refunding or voiding a settled order automatically reverses the points earned and returns any points redeemed.

POS Terminal Workflow

  1. Cashier authenticates via PIN pad on the terminal
  2. Select order type: Dine-In, Takeaway, or Delivery
  3. For Dine-In: select table from the interactive floor plan
  4. Optionally attach a loyalty member by mobile number — tier and points balance shown on the order
  5. Browse menu by category; search by item name in Arabic or English
  6. Add items, select required/optional modifiers, add per-item notes
  7. Send to Kitchen at any point — items routed to the correct KDS station
  8. Process payment — select one or multiple tender types for split payment, including loyalty points (OTP-verified)
  9. Print receipt to thermal printer and/or send a digital receipt (shows points earned and new balance)
  10. Order closed; ingredient deductions trigger automatically from stock and loyalty points are posted to the member

Security & Non-Functional Requirements

Security Controls

  • JWT access tokens expire in 15 minutes; refresh tokens rotate on every use
  • Cashier PIN login: 4–6 digit PIN, bcrypt-hashed, lockout after 5 failed attempts
  • Role-based permissions enforced at both API middleware and Prisma query level
  • All PII fields encrypted at rest; database connections over TLS only
  • Rate limiting and brute-force protection on all authentication endpoints
  • Full audit log for sensitive operations: voids, discounts, refunds, stock adjustments, loyalty point adjustments
  • Loyalty redemption requires a one-time SMS code (5-minute expiry, 3 attempts); manual point adjustments need manager approval
  • Customer data handled in line with the Saudi Personal Data Protection Law (PDPL); marketing consent captured explicitly at enrolment
  • Branch-scoped API: JWT claims prevent access to data outside assigned branches

Offline Resilience

The POS terminal uses a Service Worker and IndexedDB local cache for the active menu and open orders. If internet connectivity is lost, the terminal continues processing orders and cash payments. All transactions sync automatically when connectivity is restored, with conflict detection for concurrent edits. Loyalty points earned offline are queued and posted on sync; points redemption requires a live connection to prevent the same points being spent twice.

Key Design Decisions

Multi-tenancy strategy
Shared DB + row-level isolation
Simpler ops than schema-per-tenant; scales to many brands without migration complexity
Translation storage
JSONB per translatable field
Avoids join-heavy translation tables; fast reads; trivial to extend to a third language
Real-time layer
Socket.io over REST polling
Sub-second KDS updates are critical for kitchen efficiency and order accuracy
Inventory deduction
Event-driven on payment settle
Stock deducted only on confirmed sale — avoids ghost deductions from abandoned orders
Recipe cost calculation
Dynamic on request, Redis-cached 5 min
Always reflects latest ingredient cost; cache avoids recalculation on every page load
Offline POS mode
Service Worker + IndexedDB
Branch operations must survive internet outages; sync-on-reconnect handles reconciliation
Delivery platform sync
Webhook-first, polling fallback
Webhooks give real-time ingestion; polling fallback for platforms without webhook support
Frontend state split
Zustand (cart) + TanStack Query
POS cart needs instant local updates; server data benefits from automatic cache + refetch
Print architecture
Node bridge on local network
Browsers cannot access COM/USB ports; lightweight local Node process bridges ESC/POS
Loyalty points storage
Append-only ledger + cached balance
Every point movement is traceable for audit, expiry, and reversals; the cached balance keeps POS lookups instant
Loyalty scope
Group-wide wallet, brand-configurable
Cross-brand earning and redemption drives traffic between the group's brands; brands can opt out to run their own program
Tax module
Schema-ready, UI-disabled
tax_rate and tax_inclusive columns exist in schema for future enablement without migration
